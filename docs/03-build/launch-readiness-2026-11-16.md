# 출시 준비 구현 및 인수인계 — 2026-11-16

## 현재 판정

로컬 코드와 마이그레이션 구현 결과다. 운영 반영 완료 또는 유료 출시 승인을 뜻하지 않는다. 기존 미커밋 변경을 보존했으며, 운영 DB 변경·실결제·실제 송금·외부 이메일 발송은 하지 않았다.

원격 main의 추가 커밋 33개(`c08b76d`까지)를 `feat/launch-readiness-20261116`에 통합했다. 원격의 강사 작업 공간·승인·포트폴리오·수업 검색 UI를 유지하면서 출시 보완 기능을 연결했다. 신규 SQL은 `0036`~`0048`로 배치했다. 상세 결정과 배포 주의점은 [원격 통합 검토](./remote-integration-2026-11-16.md)에 기록했다. 현재 Git 토큰에는 workflow 권한이 없어 CI 설정은 `docs/operations/github-actions-ci.yml.example`에 비활성 템플릿으로 보존했다. GitHub Actions가 활성화된 상태는 아니다.

실행 결과와 한계는 아래에 구분한다. 대표자의 정책·사업자 정보·외부 계정 설정이 없는 상태에서 법적 정책, 환불 금액, 송금 완료 또는 개인정보 삭제를 임의로 확정하지 않았다.

추가로 실제 청구 없는 Toss 테스트 결제 모드를 구현했다. `PAYMENTS_MODE=test`와 테스트 API 개별 연동 키로 사용하며 실결제 개시 조건은 유지한다. 테스트 주문·결제는 별도로 표시하고 실매출·정산·출금에서 제외한다. `0049_test_payments.sql`과 선행 SQL이 필요하며 실제 DB에는 적용하지 않았다. 키 발급과 설정은 [테스트 결제 안내](../operations/test-payments.md)에 정리했다. 현재 테스트 키 두 개는 발급 전이므로 실제 Toss 승인 테스트는 아직 수행하지 않았다.

이후 `0050_admin_mock_checkout.sql`과 관리자 전용 모의 결제 API·버튼을 추가했다. Toss 키 없이 자신의 예약을 테스트 결제로 확정하고 예약 완료 화면으로 이동한다. 일반 사용자 접근, 타인 예약 확정, 중복 결제, 모의 거래 키의 외부 전송을 차단하며 실정산 제외 규칙을 유지한다. 운영 사이트에는 이전 결제 코드가 배포된 상태임을 공개 API로 확인했다. 현재 작업 환경에 DB 배포 자격 증명과 Vercel 배포 토큰이 없어 운영 DB 적용·배포는 수행하지 않았다.

## 배포 순서

1. 현재 운영 DB 마이그레이션 이력을 확인한다. 이미 적용된 SQL을 무작정 재실행하지 않는다. 원격 기존 이력에는 `0017_chat_search.sql`과 `0017_home_curation.sql`의 버전 중복이 있다. 실제 적용 이력과 스키마를 비교해 배포 도구의 이력을 먼저 정리해야 한다. 적용 여부를 모르는 기존 파일을 임의로 재번호화하지 않았다.
2. 운영과 분리된 검증 DB에 미적용 마이그레이션을 번호순으로 적용한다. 원격 기존 `0035`까지가 선행되며 현재 신규 범위는 `0036`~`0050`이다. `0049`는 이후 추가한 테스트 결제 환경 분리다. 이전 출시 브랜치의 `0021_google_signup_role.sql`~`0032_payment_details.sql`은 배포 전 번호 충돌을 피하기 위해 이동했으므로 양쪽 사본을 함께 적용하면 안 된다.
3. 검증 DB에서 실제 로그인 계정의 RLS·RPC·Storage·OAuth를 확인한다. 로컬 테스트의 Auth·Storage·cron 대역은 호스팅 설정까지 검증하지 않는다.
4. `0040`은 생성 인물 사진이 있는 기존 프로필을 데모로 분류하고, 승인된 실제 선생님만 공개 검색·판매를 허용한다. 실제 선생님 정보 확인 후 관리자에서 데모 해제·심사를 진행한다. 이를 하지 않으면 공개 목록이 비어 있을 수 있다.
5. `0037`은 회의 링크를 비공개 테이블로 옮기고 기존 공개 세션 컬럼의 링크를 비운다. 허용 도메인이 아닌 기존 링크는 자동 이관되지 않으므로 선생님이 새 화면에서 등록해야 한다. `0048`은 기존 강사 편집 RPC도 비공개 저장소로 연결하고 공개 컬럼에 새 링크를 쓰는 것을 차단한다.
6. 사업자·정책·결제·메일·정기 실행 설정을 완료하고 아래 체크를 통과시킨다. 정책 안내 초안은 실제 사업에 맞는 최종 문서로 교체해야 한다. 공개 플래그만 바꾸는 것으로 정책 검토가 완료되지 않는다.
7. 운영 DB 백업과 Storage 파일 백업을 확보한 후 검증된 DB 마이그레이션·코드를 함께 배포한다. 코드만 먼저 배포하면 신규 RPC가 없는 화면에서 오류가 난다.
8. 실제 사용자 계정의 가입→인증→예약→결제→입장→출석→후기→정산, 취소·전액 환불과 관리자 MFA를 테스트 환경에서 확인한다. 외부 결제 테스트 키 통합 검증과 실운영 소액 거래 확인은 별도다.

DB 함수는 금액·상태·권한을 서버에서 검사한다. 클라이언트 환경 변수만으로 금융 쓰기 권한을 열지 않는다. 서비스 키는 서버에만 둔다.

## 외부 설정

`.env.local.example`에 필요한 이름과 용도를 기록했다. 실제 키를 문서·소스·로그·PR에 넣지 않는다.

- `APP_ORIGIN`: 실제 HTTPS 도메인. 테스트 키에서는 localhost도 허용한다.
- 운영자 정보: `NEXT_PUBLIC_OPERATOR_NAME`, `NEXT_PUBLIC_BUSINESS_REGISTRATION`, `NEXT_PUBLIC_BUSINESS_ADDRESS`, `NEXT_PUBLIC_SUPPORT_EMAIL`
- 결제: `NEXT_PUBLIC_TOSS_CLIENT_KEY`, `TOSS_SECRET_KEY`는 같은 모드의 API 개별 연동 `*_ck_*` / `*_sk_*` 키를 사용한다. 주문서형 `*_gck_*` 키는 이 어댑터의 대상이 아니다.
- 웹훅: `PAYMENT_WEBHOOK_SECRET`을 충분히 긴 무작위 ASCII 값으로 설정하고, Toss에서 `/api/payments/webhook?token=<값>`을 등록한다. URL의 토큰을 로그·분석 도구에 기록하지 않도록 호스팅 측에서 관리한다. 웹훅 본문은 신뢰하지 않고 PG API로 결제를 다시 조회한다.
- 정기 작업: `CRON_SECRET`과 함께 `GET /api/jobs/maintenance`를 1~5분 간격으로 실행한다. `Authorization: Bearer <CRON_SECRET>`이 필요하다. 실행 시간은 결제 조회·취소와 메일 발송에 맞춰 최소 60초를 지원해야 한다. 스케줄러/요금제의 빈도 제한은 실제 계약에서 확인한다.
- 메일: `RESEND_API_KEY`, `EMAIL_FROM`과 발신 도메인 검증이 필요하다. 이 작업은 서비스 알림용이다. Supabase 가입·복구 메일의 SMTP·발신자·리다이렉트 허용 목록은 별도로 설정한다.
- Auth 리다이렉트: 실제 도메인의 `/auth/callback`을 등록하고 가입·복구 메일 템플릿의 PKCE code 교환 흐름을 실제 기기에서 확인한다. 다른 브라우저에서 열었을 때의 동작도 검증한다.
- `PAYMENTS_ENABLED=true`, `NEXT_PUBLIC_POLICIES_PUBLISHED=true`는 최종 정책과 모든 연동 검증 후에만 설정한다. 결제 코드는 키 종류·도메인·사업자 정보·정기 작업 비밀값이 빠지면 계속 유료 결제를 차단한다.

정기 작업은 실행할 때마다 이력을 남기며 관리자에 표시한다. DB의 기존 예약 정리 cron과 함께 실행되어도 예약 완료·만료 처리는 반복 실행 가능하다. 메일은 동시 작업 간 리스로 분리하며, 공급자의 24시간 멱등 범위를 넘은 불확실한 전송은 자동 재발송하지 않고 확인 대상으로 남긴다. 대량 트래픽에서는 처리량·적체를 보고 워커 수와 배치 크기를 조정해야 한다.

## 검증 방법과 실제 수행 범위

```text
npm run db:types
npm run type-check
npm run lint
npm test
npm run build
npm run release:check
```

- `db:types`는 로컬 마이그레이션으로 구성한 실제 PostgreSQL(PGlite) 스키마에서 타입을 생성한다. 운영 DB와의 드리프트는 배포 시 실제 프로젝트 타입/카탈로그와 추가 대조해야 한다.
- 관리자 모의 결제 추가 후 자동 검증: 단위·DB·API 및 원격 SQL 회귀 테스트 98개, 타입 검사, 경고를 허용하지 않는 lint, 프로덕션 빌드. 브라우저 검증은 외부 쓰기를 대역으로 처리한 범위다. 테스트 결제의 동의 분리·환경 혼용 차단·환불·실정산 제외, 관리자 모의 결제의 권한·소유권·멱등성과 완료 화면 이동도 검증한다.
- DB 테스트는 모든 마이그레이션과 주문·환불·쿠폰 잠금·권한·출석·검색·휴무·일정 변경·자료·계정 제한·채팅 흐름을 실행한다. Auth·Storage 서비스·cron 스케줄러 자체는 최소 대역으로 구성한다.
- API 테스트는 교차 출처·잘못된 본문·과대 요청 거절, PG 응답 대조·멱등 헤더·타임아웃을 확인한다.
- 실제 Chrome에서 기존 가입·로그인 이동/뒤로 가기를 검증했다. 신규 화면은 390px·1440px에서 실제 React 컴포넌트와 로컬 RPC 응답으로 검증했다. 외부 이메일·결제·송금 쓰기는 대역 처리했다.
- 브라우저 명령: `TEST_BASE_URL`과 선택적 `CHROME_PATH` 설정 후 `node tests/navigation.browser.cjs`, `node tests/launch.browser.cjs`. 검증용 서버는 해당 빌드의 `NEXT_DIST_DIR`로 실행해야 한다.
- 현재 로컬 설정 검사는 13개 미설정/미확정 항목을 보고한다. 실제 값은 출력하지 않는다.
- `npm audit`는 의존성 메타데이터의 외부 전송을 이유로 자동 승인 검토에서 거절되어 실행하지 않았다. 공개 Next.js 보안 공지를 직접 확인해 프레임워크·이미지 처리 버전을 갱신했다. 전체 의존성 취약점 검사 완료를 주장하지 않는다.

## 선생님 앱 0.1 안드로이드 테스트

### 구현 범위와 현재 상태

`apps/mobile`은 웹과 독립된 Expo SDK 58·React Native 앱이다. 별도의 `package.json`·lockfile·TypeScript 설정을 사용하며 웹 TypeScript 검사에서 제외한다. 서버·DB는 기존 고쌤과 공유한다. 현재 앱 소스 버전은 `apps/mobile/package.json`의 `0.1.1`, 변경 기록은 `apps/mobile/releases.json`이다. Expo 설정은 같은 버전을 읽고 EAS는 네이티브 빌드 번호를 자동 증가시킨다.

- 이메일·비밀번호 로그인, 보안 저장소의 세션 저장, 선생님 역할 확인, 홈·알림함·채팅·수업 신청/예약·설정을 구현했다. Google 로그인은 아직 앱에 연결하지 않았다. Google 가입자는 웹의 비밀번호 복구로 비밀번호를 설정한 뒤 테스트할 수 있다.
- 채팅 목록·읽기·이전 메시지·전송·실시간 갱신, 신청과 확정 구분, 서버 시각에 따른 수업 입장 확인을 제공한다. 자료·프로필·정산·출석 편집 등 기존 상세 기능은 시스템 브라우저의 웹 화면으로 연결하며 별도 웹 로그인이 필요할 수 있다. 앱 토큰을 URL이나 WebView에 전달하지 않는다.
- 채팅·수업 신청/확정 알림, 수업 시작 15분 전, 24시간 이내 링크 미등록, 종료 30분 이후 출석 미확정 알림을 기기별 푸시 대기열에 연결한다. 준비 알림은 같은 회차·일정·종류마다 한 번만 생성한다. 출석 알림은 최근 7일을 대상으로 한다. 새 후기에 대한 기존 알림도 푸시 대기열로 전달한다.
- 기기별 등록, 수신 종류·조용한 시간, 로그아웃 전 등록 해제, 만료 기기 처리, 공급자 오류/receipt 확인을 지원한다. 잠금 화면에는 채팅 본문·학생 이름 대신 일반 안내를 보낸다. Expo 접수나 Google/Apple 전달 접수는 실제 기기 표시 완료와 구분한다.
- 앱의 설정 화면에서 5초 후 로컬 알림, 본인 기기의 채팅/수업 신청 원격 테스트, 최근 발송 상태 조회를 제공한다. 테스트는 실제 예약·메시지를 만들거나 메일을 보내지 않는다. 조용한 시간과 수신 설정은 테스트에도 적용된다.

현재 Expo·Firebase 계정은 아직 연결하지 않았다. 설치용 APK 생성, 실제 안드로이드 기기 설치·수신 검증, 운영 DB 적용·서버 배포는 미수행이다. 로컬 Android Hermes 번들 컴파일과 자동 테스트는 실제 FCM 수신을 검증하지 않는다.

초기 로컬 검증은 전체 자동 테스트 120개, 웹·앱 각각의 타입 검사, 웹 ESLint, Next.js 프로덕션 빌드와 Android Hermes 번들 컴파일을 통과했다. 기기 연결 해제와 등록이 동시에 실행되는 경우의 재등록 방지, 기기 소유권·대기열·조용한 시간·receipt 상태·Unicode 보안 저장소도 테스트한다. 0.1.1에서 앱의 localhost 웹 주소를 저장소의 운영 주소 `https://vora-bice.vercel.app`로 수정했다. 현재 앱 설정 검사는 Expo 프로젝트 ID와 Firebase 파일 미설정을 보고한다.

0.1.1의 준비 상태는 `npm run mobile:readiness`로 로컬 계정·서버 푸시 설정을 확인하고, `npm run mobile:readiness -- --remote`로 실제 배포 상태까지 읽기 전용으로 확인할 수 있다. 결과는 비밀 값 없이 `.tmp/mobile-readiness.json`에 저장한다. 2026-11-17 실제 조회에서는 `lesson_feedback`와 `mobile_push_devices`가 HTTP 404였고 모바일 테스트 경로가 HTTP 307로 응답했다. 새 DB·서버 기능이 준비된 것으로 판정하지 않았다. 이 명령은 SQL을 적용하거나 알림을 발송하지 않는다.

0.1.1 검증은 전체 자동 테스트 123개, 웹·앱 타입 검사, ESLint와 변경된 설정을 포함한 Android Hermes 번들 컴파일을 통과했다. `local-server-*` 항목은 로컬 `.env.local`의 준비 상태이며 운영 Vercel 환경 설정을 검증한 결과와 구분한다. 설치용 APK와 실제 푸시는 Expo·Firebase 계정 연결 후 검증해야 한다.

### 최초 연결 순서

1. 루트에서 `npm run mobile:setup`을 실행한다. 기존 웹의 **공개 Supabase URL·anon 키만** 앱의 gitignored `.env`로 복사한다. `.env`가 있으면 보존한다. `EXPO_PUBLIC_WEB_ORIGIN`은 실제 배포된 HTTPS 웹 주소로 설정한다. 앱에 서비스 역할 키·FCM 서비스 계정·Expo 서버 토큰을 넣지 않는다.
   기존 `.env`가 localhost를 가리키면 `node scripts/setup-mobile-env.cjs --web-origin=https://vora-bice.vercel.app`로 웹 주소만 갱신할 수 있다. 다른 연결값은 보존한다.
2. `cd apps/mobile`에서 `npm ci` 후 `npx eas login`, `npx eas init`으로 본인 Expo 계정의 프로젝트를 연결한다. 발급된 프로젝트 UUID를 `.env`의 `EXPO_PUBLIC_EAS_PROJECT_ID`에 넣는다. 앱 패키지 ID는 `com.gossaem.teacher`다.
3. Firebase 콘솔에서 프로젝트와 Android 앱 `com.gossaem.teacher`를 등록한다. 받은 `google-services.json`은 `apps/mobile/google-services.json`에 둔다. FCM HTTP v1 설정을 완료하고 `npx eas credentials --platform android`에서 해당 Firebase 프로젝트의 FCM v1 서비스 계정을 연결한다. 서비스 계정 JSON은 저장소에 커밋하지 않는다.
4. EAS 프로젝트의 `preview` 환경에 앱 `.env`의 `EXPO_PUBLIC_*` 값을 등록한다. `GOOGLE_SERVICES_JSON`은 `google-services.json` 내용의 **file** 환경 변수로 등록한다. `development`·`production`은 각각 별도 환경을 사용한다. gitignored 로컬 `.env`만으로 클라우드 빌드에 값이 전달된다고 가정하지 않는다.
5. 검증 DB에서 기존 미적용 이력과 `0051`을 확인한 뒤 `0052_mobile_push.sql`을 적용한다. 신규 RPC·표·권한이 포함되며 Expo 토큰 원본은 일반 계정이 조회할 수 없다. 웹 서버 코드도 함께 배포한다.
6. Expo 프로젝트에서 enhanced push security를 활성화한다. 웹 서버에 `PUSH_ENABLED=true`, `EXPO_PUSH_ACCESS_TOKEN`, `EXPO_PUSH_PROJECT_ID`와 기존 Supabase 서버 연결·`CRON_SECRET`을 설정한다. 기존 `/api/jobs/maintenance`가 푸시도 처리한다. 또는 `/api/jobs/push`를 1분 간격으로 실행하고 `Authorization: Bearer <CRON_SECRET>`을 설정한다. 작업을 중복 실행해도 대기열을 리스로 분리한다. 두 스케줄을 모두 만들 필요는 없다.
7. 루트의 `npm run mobile:check`에서 누락 설정을 확인하고 `npm run mobile:build:android`를 실행한다. `preview`는 개발 서버 없이 실행되는 설치용 APK다. EAS가 제공한 APK URL을 안드로이드에서 열어 설치한다. 최초 빌드 시 Android 서명 키를 EAS에 생성·보관하고 같은 앱의 이후 버전에도 유지한다.
8. 개발 중에는 `apps/mobile`에서 `npm run build:development`로 개발 APK를 만든 뒤 `npm start`로 Metro에 연결할 수도 있다. 안드로이드 원격 푸시는 Expo Go로 검증하지 않는다.

### 실제 기기 확인 순서

1. 선생님 계정으로 로그인 → 설정 → 휴대폰 알림 허용·기기 등록.
2. 로컬 알림 테스트를 눌러 5초 후 알림 표시를 확인한다. 이것만으로 서버·FCM 검증이 완료된 것은 아니다.
3. 채팅 원격 테스트와 수업 신청 원격 테스트를 각각 누르고 앱을 백그라운드로 전환한다. 알림을 선택해 채팅 목록/신청 목록이 열리는지 확인한다. 설정의 최근 발송 상태에서 실패 코드를 볼 수 있다.
4. 별도의 학생 계정에서 실제 테스트 메시지를 보내고, 선생님 앱이 켜져 있을 때·백그라운드일 때·일반적으로 닫힌 상태일 때 수신과 해당 대화 이동을 확인한다. 테스트 DB의 무료/테스트 예약으로 신청·확정 알림을 확인한다. 테스트 버튼은 실제 학생 계정의 메시지/예약 흐름 검증을 대신하지 않는다.
5. 채팅 수신 끄기·조용한 시간·기기 연결 해제를 확인한다. 웹에서 채팅/수업 알림을 꺼둔 경우 기존 정책에 따라 원본 알림 자체가 생성되지 않을 수 있다.
6. 로그아웃한 뒤 이전 계정의 알림이 새로 발송되지 않는지, 다른 계정으로 로그인했을 때 이전 대화가 열리지 않는지 확인한다. 이미 OS에 전달된 알림과 강제 중지·제조사 절전·네트워크 상태에 따른 지연은 별도 확인한다. 알림함을 항상 함께 제공한다.

### 버전 관리와 재현 명령

```text
npm run mobile:type-check
npm --prefix apps/mobile run export:android
npm test
npm run lint
npm run build
npm --prefix apps/mobile run version:patch
```

`version:patch`/`version:minor`는 앱 package·lockfile·변경 기록을 함께 갱신한다. 소스 버전은 Git 커밋 후 `mobile-v0.1.0` 형식으로 태그하고, 같은 버전의 재빌드는 EAS의 별도 빌드 번호로 구분한다. 버전과 빌드 번호는 앱 설정에 표시한다. 서명 키가 달라지면 기존 APK 위에 업데이트 설치가 되지 않으므로 키를 재생성하지 않는다.

첫 개발 소스는 `mobile-v0.1.0-dev.1`로 구분한다. 실제 APK 검수 전 개발 태그이며 스토어 출시나 기기 수신 검증 완료를 뜻하지 않는다.

푸시는 네트워크 결과가 불확실한 전송을 자동 재시도하지 않고 `uncertain`으로 남긴다. 명확한 요청 제한은 제한적으로 재시도하고, 토큰 폐기는 기기 비활성화로 처리한다. 수신 receipt는 약 15분 후부터 확인하므로 테스트 직후 `accepted`는 정상적인 중간 상태다. 일반 대기열은 24시간, 수업 시작 알림은 15분 경과 시 생략하며 기기 등록은 30일 동안 갱신되지 않으면 발송 대상에서 제외한다.
