# Toss 테스트 결제 설정

## Toss 키 없이 다음 화면 확인하기

관리자 계정은 유료 결제가 비활성화된 동안 결제 화면에서 **모의 결제로 예약 확정 (관리자)** 버튼을 사용할 수 있다. 카드나 Toss 키 없이 자신의 예약을 테스트 결제로 확정하고 기존 예약 완료 화면으로 이동한다. 일반 계정에는 제공하지 않으며 서버와 DB에서 관리자 권한·예약 소유권을 다시 검사한다.

이 기능은 `0050_admin_mock_checkout.sql`과 선행 마이그레이션까지 반영된 DB 및 최신 코드 배포가 필요하다. 코드만 기능 브랜치에 푸시해도 main을 배포한 기존 사이트 화면이 자동으로 바뀌지는 않는다. 배포 브랜치를 확인해야 한다.

2026-11-16에 저장소에 기록된 `https://vora-bice.vercel.app/api/payments/config`를 확인한 결과 `enabled=false`였고 `mode`·`mockAvailable` 필드가 없었다. 이전 결제 코드가 배포된 상태이므로 새 코드 배포가 필요하다. 당시 운영 DB 마이그레이션과 배포 자체는 수행하지 않았다.

`PAYMENTS_ENABLED=true`이거나 라이브 키가 설정되어 있으면 모의 결제는 차단한다. 필요하면 `ALLOW_ADMIN_MOCK_CHECKOUT=false`로 별도 비활성화할 수 있다. 모의 결제 금액은 테스트로 표시되며 실제 정산·출금·실매출에 포함되지 않는다. 관리자 MFA 환불 기능으로 취소할 때도 외부 결제사를 호출하지 않는다. 실제 Toss SDK·인증·승인을 검증하려면 아래 테스트 키 방식으로 진행한다.

`PAYMENTS_MODE=test`에서는 Toss API 개별 연동 테스트 키로 결제창·승인·취소를 검증한다. 사업자 정보·최종 정책 공개·유료 결제 개시 플래그는 테스트 개시 조건에서 제외한다. 실결제 모드는 기존 출시 조건을 모두 유지한다.

테스트 키를 사용하면 실제 결제수단에서 돈이 출금되지 않는다. [Toss 테스트 환경 안내](https://docs.tosspayments.com/guides/v2/get-started/environment)

## 1. 테스트 키 발급

1. [Toss 개발자센터](https://developers.tosspayments.com/)에 로그인한다.
2. 테스트 상점의 **API 키 → API 개별 연동 키**에서 클라이언트 키와 시크릿 키를 확인한다.
3. **같은 세트**의 `test_ck_...`와 `test_sk_...`를 사용한다. 현재 코드는 결제창 연동이므로 위젯용 `test_gck_...`·`test_gsk_...` 키와는 다르다.
4. 실제 키는 채팅·스크린샷·Git에 올리지 않고 로컬 `.env.local` 또는 배포 서비스의 환경변수에만 저장한다. `TOSS_SECRET_KEY`에는 `NEXT_PUBLIC_`를 붙이지 않는다.

[Toss API 키 안내](https://docs.tosspayments.com/reference/using-api/api-keys)

## 2. 환경변수

[환경변수 예시](../../.env.test-payments.example)를 참고해 `.env.local`에 설정한다. 기존 Supabase 연결 값은 유지한다.

```dotenv
PAYMENTS_MODE=test
APP_ORIGIN=http://localhost:3005
NEXT_PUBLIC_TOSS_CLIENT_KEY=test_ck_발급받은_클라이언트_키
TOSS_SECRET_KEY=test_sk_발급받은_시크릿_키
PAYMENTS_ENABLED=false
NEXT_PUBLIC_POLICIES_PUBLISHED=false
```

위 키 값은 설명용이며 동작하지 않는다. 발급받은 실제 테스트 키로 바꿔야 한다. 개발 서버 기본 포트는 `3005`다. 다른 포트나 배포 도메인을 사용하면 `APP_ORIGIN`을 **브라우저 주소의 origin과 정확히 동일하게** 지정한다. 공개 테스트 서버는 HTTPS가 필요하며 HTTP는 localhost/127.0.0.1에서만 허용한다.

```sh
npm run payments:test:check
npm run dev
```

설정 후 개발 서버를 재시작한다. 배포 환경변수를 바꾼 경우 재배포한다. 검사 명령은 설정 유무·키 종류만 출력하며 키 원문을 출력하지 않는다. 실제 키 유효성과 DB 반영 여부는 테스트 결제를 통해 확인한다.

## 3. 테스트 DB 준비

테스트 계정과 운영과 분리된 Supabase 프로젝트를 사용한다. 이 구현에는 `0049_test_payments.sql`이 필요하며, 원격 기존 스키마와 출시 마이그레이션 `0036`~`0048`이 먼저 반영되어야 한다. 이번 작업은 운영 DB에 SQL을 실행하지 않았다.

기존 저장소에 `0017` 버전 파일 두 개가 있으므로 최초 적용 또는 CLI 배포 전 실제 DB 이력을 대조해야 한다. 이미 적용된 SQL을 반복 실행하거나 기존 파일을 임의로 재번호화하지 않는다. [통합 검토의 배포 전 확인](../03-build/remote-integration-2026-11-16.md)을 참고한다.

## 4. 결제 흐름 확인

1. 승인된 테스트 선생님이 미래 시간의 유료 수업을 게시한다. 데모 표시와 계정 제한이 있으면 먼저 테스트 계정 상태를 확인한다.
2. 테스트 학생으로 예약하고 15분 안에 결제 화면을 연다.
3. 화면의 **테스트 결제·실제 청구 없음** 안내와 **테스트 결제창으로 이동** 버튼을 확인한다.
4. Toss 테스트 결제창에서 인증을 마친다. 성공 URL 진입 후 서버의 실제 Toss 승인 API 검증까지 완료되어야 예약이 확정된다. 클라이언트 버튼만으로 성공 처리하지 않는다.
5. 결제 내역의 **테스트** 표시와 예약 확정을 확인한다. Toss 개발자센터의 테스트 결제 내역에서도 주문을 확인한다.
6. 관리자 MFA 계정에서 전액 취소·환불을 검증한다. 테스트 금액은 실정산·출금 잔액·관리자 실매출에 반영되지 않는다.

테스트 결제도 예약·좌석·쿠폰·출석·알림에 실제 테스트 데이터를 만든다. 실사용자 수업과 쿠폰을 사용하지 않는다. 테스트 주문을 실결제 키로 처리하거나 실결제 주문을 테스트 키로 처리하면 서버가 차단한다. 모드를 바꾼 뒤 이전 예약을 다시 사용하면 환경 충돌이 나므로 해당 환경에서 기존 주문을 정리하거나 새 예약으로 진행한다.

## 5. 선택 사항: 웹훅·정기 복구

브라우저의 승인 완료까지 테스트하는 데 웹훅·정기 작업 설정은 필수가 아니다. 서버 재시도·지연 승인·브라우저 종료 후 복구까지 테스트하려면 별도로 `PAYMENT_WEBHOOK_SECRET`, `CRON_SECRET`을 설정하고 테스트 서버를 외부에서 접근 가능한 HTTPS 주소로 배포한다.

- Toss 웹훅 수신 URL: `https://테스트도메인/api/payments/webhook?token=설정한_비밀값`
- 정기 실행: 기존 유지보수 API 설정을 사용한다. 현재 키와 동일한 결제 환경의 주문만 복구한다.
- 웹훅 이벤트 내용만 신뢰하지 않고 Toss 조회 API로 주문·금액·결제 키를 재검증한다.

## 실결제 전환

실결제 전환은 별도 출시 작업이다. 테스트 설정이 실제 결제 허용을 뜻하지 않는다. `PAYMENTS_MODE=live`, 같은 세트의 라이브 API 개별 연동 키, `PAYMENTS_ENABLED=true`, 최종 정책 공개, 사업자 정보, HTTPS 주소, 웹훅·정기 작업 설정과 외부 계약 검증이 모두 필요하다. 테스트 주문·결제 데이터는 테스트 환경으로 표시되어 계속 실정산에서 제외된다.
